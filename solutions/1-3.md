## 一句話題意

原本是完全圖，給你被刪掉的 m 條邊，求剩下的圖（補圖）有幾個連通塊、每塊多大。

## 卡住的地方

- 一開始想用「分裂」的方式做，但不知道要怎麼維護。後來發現方向是對的：把「還沒走到的島」放在一個集合裡，BFS 時一座一座分出去。
- 看不懂為什麼「每次都掃整個集合」不會變成 O(n²)，這裡用到了均攤分析。
- 不知道怎麼記錄一個航運圈的大小：每次 BFS 開始時把計數器設成 1，每移出一座島就加 1，佇列空了就存起來。
- 第一版外層用 `for j = 0..n-1`，不是真正的 BFS：被移出的島沒有再往外走，航運圈之間也沒有分開。改成「`mylist` 還有島就開新的一圈」加上一個 `bfs` 佇列才對。
- 速度一直超時：
  - `find` 掃整個 `bre`，每次 O(m)。
  - 改成 `stop[s]` 後，`find` 還是在迴圈裡，處理一座 s 的花費是「mylist 長度 × `stop[s]` 長度」。在 #21（島 1 和其他所有島都停駛）裡，這會是 4×10¹⁰。
  - 最後把標記移到迴圈外，乘法才變成加法。

## 關鍵想法

- 補圖的邊太多，不能建出來，**只用停駛的邊來判斷「哪些走不到」**。
- `mylist` 用 `queue`：一開始記下長度 len，拿出 len 次。要留下的島 push 回尾巴，走得到的島就不放回去，改放進 `bfs`。
- 均攤分析：每看一座島，結果只有兩種。
  - 被移出：總共 ≤ n 次。
  - 因為停駛而留下：總共 ≤ 2m 次。
  - 所以總共 O(n + m)。
- 不能開 n×n 的二維表格查「s–v 停駛嗎」。但同一時間只會用到第 s 列，所以用**一條一維陣列 `mark`** 代表「目前這一列」：處理 s 之前，先把 `stop[s]` 標記上去，之後每次查詢 O(1)。

## 下次看到什麼，就想到什麼

- 看到「原本全部相連，刪掉一些邊」或「補圖」 → 想到用「還沒走到的點」集合做 BFS，每次只用刪掉的邊判斷哪些走不到。
- 看到「迴圈裡面呼叫 `find`」 → 想到把答案先標記在陣列上，讓查詢變成 O(1)。
- 看到「一個看似 O(n²) 的掃描，但每次掃到的東西不是被刪掉、就是用掉一個有限的資源」 → 想到均攤分析，總花費 = 被刪的次數 + 資源的總數。

## 寫程式時犯的錯

- `find(..., {x, com})`：大括號沒有型態，編譯錯誤。要寫成 `pair<int,int>{x, com}`。
- `mylist` 存 0 開始的編號，`bre` 存 1 開始的編號，查詢永遠對不上。
- 停駛航線只查 `{s, com}`，漏了 `{com, s}`。
- `continue` 跳過了 `mylist.pop()`。
- `for(int j=0;j<n;i++)`，迴圈變數寫錯。
- `find` 放在迴圈裡，O(n·m) 超時。

## 還可以更好的地方

- **第 40 行在 `while` 迴圈裡開 `vector<bool> mark(n,false)`**：每處理一座 s，都要重新開一條長度 n 的陣列。s 總共有 n 座，所以這部分其實是 O(n²)。這次能過，是因為 `vector<bool>` 一格只佔 1 bit，清成 0 非常快，最慢的一筆跑了 0.31 秒，時限是 1 秒。我實際把它換成 `vector<int>` 測過，#21、#23、#25 會超過 1 秒而 TLE。改進方式：把 `mark` 開在迴圈外，存 `s` 而不是 `true`，判斷時寫 `mark[com] == s`，就不用每次重開。
- `bre`、`out` 已經沒有用到，可以刪掉。
- `i<stop[s].size()` 會出現 `-Wsign-compare` 警告，可以寫成 `i<(int)stop[s].size()`，或改用 `for (int v : stop[s])`。
